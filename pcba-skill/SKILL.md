# PCBA Skill (EasyEDA + JLCPCB)

## Core Rule

Treat EasyEDA data, generated BOM, and the JLCPCB quote page as three separate states. A change is complete only when all three agree:

- EasyEDA project source contains the new part and no stale old part.
- Generated BOM contains the new supplier part and manufacturer part, and excludes the old one.
- Freshly regenerated JLCPCB quote page shows no shortage/unmatched row for the changed part.

If the quote still shows an old component, assume the page or order data is stale until proven otherwise. Regenerate `Order PCB/FPC at JLCPCB` and open the new URL.

Do not conflate EasyEDA's order-data confirmation with JLCPCB's final order. It is acceptable to confirm EasyEDA's "Order data generated finish" dialog to open a fresh quote URL, but never submit the final JLCPCB purchase, payment, or irreversible order unless the user explicitly authorizes that exact final action. If the user says a human will order, stop at the regenerated quote/order-prep page.

## Workflow

1. Gather the active project state before editing.
   - Identify the exact designator, value, package, supplier part, manufacturer part, footprint, quantity, and shortage.
   - Inspect the current EasyEDA source or generated BOM when possible, not only the visible table.
   - Use current official JLCPCB part pages or the quote page for stock; stock is time-sensitive.
   - When the user asks for a specific board name such as `Board5`, create or edit that exact board. If they ask for a new board, create a new PCB document instead of copying an existing board unless they explicitly ask for a copy.
   - After `copyBoard`, `deleteBoard`, or board rename operations, immediately inspect `getAllBoardsInfo()`, `getAllSchematicsInfo()`, and `getAllPcbsInfo()`. EasyEDA may create names such as `Board5_1`, leave orphan schematic/PCB documents, or reject document renames until stale name conflicts are deleted.

2. Select replacement parts conservatively.
   - Keep electrical value, package, footprint, assembly type, and orientation compatible.
   - Prefer JLCPCB Basic parts, then Extended parts with enough stock.
   - Check stock against required quote quantity plus attrition/loss. Do not accept a part whose available quantity is equal to or below the shortage.
   - Verify value-coded passive parts literally. For USB-C CC pull-downs, require 5.1k ohm, not 5.1 ohm.
   - Relax tolerance or rating only for clearly non-critical roles, and state the tradeoff. Example: a reset pull-up can usually tolerate a 10k 0603 +/-5% resistor; USB series resistors should keep the intended value and footprint.

3. Update both identity and manufacturing fields.
   - Replace stale supplier/manufacturer data everywhere it can affect BOM or PCBA: `Supplier Part`, `Manufacturer`, `Manufacturer Part`, `JLCPCB Part Class`, datasheet/link, part name/description, and footprint metadata when required.
   - After changing `Value`, re-check the supplier fields because EasyEDA may automatically clear `Supplier Part`.
   - Verify the target components in both PCB and schematic objects: supplier, supplier part/code, manufacturer, manufacturer part, value, package/footprint, and `addIntoBom`.
   - Keep the footprint unchanged only when the replacement package is truly footprint-compatible.
   - If a footprint changes, remove old footprint remnants from layout before placing the replacement.
   - For API-created or modified components, fetch the component after creation, set `designator`, `name`, `supplierId`, `manufacturerId`, `otherProperty`, and stable `uniqueId`, then call object setters plus `done()` when available before relying on the change. A later `getAll()` may otherwise still show `U?`, `C?`, or temporary IDs such as a dollar-sign placeholder (dollar + digit; written out here because a literal one gets substituted by slash-command args).
   - Components placed from the JLC library via `sch_PrimitiveComponent.create({libraryUuid,uuid})` come in with `supplierId` set to the **manufacturer part + ".1"** (e.g. `ATMEGA328P-AU.1`), NOT the LCSC `C`-number — JLCPCB PCBA cannot match this. **This happens even when you pass the full device object returned by `lib_Device.getByLcscIds()`/`lib_Device.search()` as `component` (not just a bare `{libraryUuid, uuid}`)** — the full object carries the correct C-number in its own `supplierId` field, but `create()` does not appear to reuse it, so do not skip the fix-up step just because you sourced the device object "the right way". Set the real C-number explicitly on the PCB component (`comp.toAsync().setState_SupplierId("Cxxxx"); setState_Supplier("LCSC"); await done()`) AND the schematic component (`sch_PrimitiveComponent.modify(pid,{supplier:"LCSC",supplierId:"Cxxxx"})`) for **every** placed component, then `pcb_Document.save()` and regenerate the BOM to confirm the "Supplier Part" column shows the C-number for all of them (a bulk `getAllPrimitiveId()` → `get()` → regex-check `/^C\d+$/` on `getState_SupplierId()` catches stragglers fast). Note: re-importing changes can re-sync this field from the library device, so trust the library value when it carries a real C-number. Look parts up fast with `lib_Device.getByLcscIds(["C14877",...])`.
   - When replacing `CH340C` with `CH340G`, remember that `CH340G` needs an external 12 MHz crystal and load capacitors. Typical net map: pin 1 `GND`, 2 `D0_RX`, 3 `D1_TX`, 4 `CH340_V3`, 5 `USB_DP_CH340`, 6 `USB_DN_CH340`, 7 `CH340_XI`, 8 `CH340_XO`, 13 `DTR`, 16 `+5V`; add a 12 MHz crystal between `CH340_XI`/`CH340_XO` and two load capacitors to `GND`.

4. Verify schematic connectivity by net names.
   - Use net labels for schematic connectivity instead of long direct wires when this simplifies the design.
   - Confirm named nets propagate to the PCB: power, ground, reset, USB D+/D-, UART, ICSP, and Arduino header nets.
   - Do not trust `SCH_Document.importChanges()`, `SCH_Netlist.setNetlist()`, or `modifySchematicName()` solely because the API returns `true`. Re-open the document and verify schematic components, PCB components, generated netlists, and DRC categories.
   - `pcb_Net.getNetlist('JLCEDA')` is documented to return two netlist strings (schematic then PCB), but in this bridge version it returned a **single JSON string** (`{components:{...}}`); parse `JSON.parse(s).components[designator].pinInfoMap` to read each pin's net. To diff schematic vs PCB, compare that against the schematic-side `sch_ManufactureData.getNetlistFile(name,'PADS')` text.
   - A persistent DRC `Netlist Error` ("Schematic Netlist <> PCB Netlist") while copper is otherwise clean is most often caused by leftover **floating named-net stub wires** in the schematic (stubs left behind after deleting/swapping a component). Find them with `sch_PrimitiveWire.getAllPrimitiveId()`→`get(id)`→`getState_Polyline()` by coordinate, delete them, save, then re-import to PCB.

5. Verify layout constraints before ordering.
   - Put the board outline on the Board Outline layer as a single closed polygon/polyline rectangle, not four independent line primitives.
   - When creating the outline through the EasyEDA API, create a closed polygon first and then place it as a polyline on Board Outline layer id `11`; verify stale outline line primitives were removed.
   - For USB connectors, align the connector mouth/nose with the intended board edge; for this project pattern, USB faces left, sits at the left board boundary, and is vertically centered.
   - Remove stale USB footprints, old pads, and disconnected remnants.
   - **Two components stacked at the SAME coordinates are invisible to DRC when their pads share nets** (e.g. two decoupling caps, both 3V3/GND, at identical x,y — same-net pad overlap raises neither clearance nor connection errors, and the render looks like one part). This shipped to production once and was only caught by JLCPCB's assembly DFM ("CXX will affect other part, could we remove?"). **Audit every board by grouping components on exact (x,y)** — one line of code — before ordering. If it reaches production anyway: approving DNP of the duplicates is usually electrically acceptable for redundant decoupling (state what remains per rail), then fix the source and reroute. **JLC's DFM phrasing for the same bug varies per board**: "will affect other part" on one order, "there is no pad for C2,C3,…" on the next (the pads get assigned to one member of each stacked pair; the OTHER member is reported padless — which member gets flagged is arbitrary, so the DNP list differs between boards with the identical bug). Map the flagged designators back to the stacked PAIRS before agreeing, and state per-rail what decoupling remains.
   - **Answering a JLC "please check polarities" DFM email rigorously:** for each orientation-critical part, read its pin-1 pad offset relative to the component origin (pad dump) and the nets on each pad, then compare against the red pin-1 dot in JLC's 2D placement render. Sensor example: VL53L1X pin1 = bottom-RIGHT at rot0; VL6180 pin1 = bottom-LEFT; SOT-23 regulators: verify by NETS (XC6206: 1=GND, 2=VOUT, 3=VIN). Caps/resistors are non-polar — say so explicitly. Reply template: (1) approve/refuse each proposed removal with reason, (2) "orientations verified against design data, pin 1 at the [corner] marker as shown, remaining parts non-polarized, please proceed."
   - Resolve component overlaps before routing. **DRC's `Clearance Error` only checks copper (pads/tracks/pours), not silkscreen or plastic-body proximity** — two components can be DRC-clean while their physical bodies visually collide (seen with a SOT-223's sparse 4-pad footprint vs. a tact switch placed on top of it). After placing/moving parts, also compute each component's pad-bounding-box (`min/max` of `getAllPinsByPrimitiveId` X/Y, expanded a few mil for body overhang) and flag any pair whose boxes overlap, even if DRC is silent. Treat this as a heuristic, not ground truth: parts with sparse/cornered pads (SOT-223, big THT connectors) can show a false-positive box overlap when the actual copper and body silhouettes don't touch — confirm borderline cases with exact pad coordinates before moving anything.
   - Mounting holes (see `references/arduino-uno-layout.md` for the standard coordinates) are a placement constraint like any other keepout — check new/moved components against them the same way as pad-to-pad clearance, since a hole added after the main layout is done can land under an already-placed part.
   - Use Arduino-compatible single-row headers where intended. Avoid accidentally selecting 2x4/2x5 headers or long-tail pin headers when the board expects normal-height female headers.
   - Preserve requested silkscreen text, such as `Designed by Codex-5.5`, unless the user asks to change it.

6. Route and inspect.
   - Use `Route > Auto Routing...` when the user asks for autorouting.
   - In the EasyEDA API, use the PCB command path for autorouting when available, then press the visible `Run`/confirm button in the autorouter dialog.
   - Confirm the routing completion log reports 100% net completion.
   - Pay special attention to USB pads, D+/D- series resistors, power, reset, ICSP, and header nets.
   - After schematic-to-PCB import, click the appropriate `Import Changes`/apply dialog button, then rerun DRC and connectivity checks.
   - If only supplier metadata changed and footprint/pads did not change, rerouting is usually unnecessary; still regenerate manufacturing data.

7. Regenerate JLCPCB order data.
   - Use `Export > Order PCB/FPC at JLCPCB` or the equivalent EasyEDA API.
   - Click/confirm the EasyEDA "Order data generated finish" dialog.
   - If EasyEDA shows a modal dialog during requested workflow steps, click the appropriate confirm/OK/continue button instead of leaving the UI blocked. This does not authorize final JLCPCB purchase/payment.
   - Open the newly generated quote URL in normal Chrome when the user wants to continue ordering.
   - If `placePcbOrder()`, `placeComponentsOrder()`, or `placeSmtComponentsOrder()` returns `false`, do not claim that a quote URL was regenerated. Fall back to `getBomFile()`, `getPickAndPlaceFile()`, and `getGerberFile()`, save the files, validate the Gerber zip, and state that quote-page verification is incomplete.
   - If the JLCPCB page is dynamic or login-gated and cannot be verified programmatically, say that quote-page shortage verification is incomplete instead of implying success.
   - Never submit the final purchase, payment, or irreversible order step unless the user explicitly authorizes that exact action.

## EasyEDA API Notes

The bridge runs `async function(eda){...}` in the EasyEDA Pro **page context**, so the DOM (`document`) is available. PCB unit = mil; schematic unit = 0.01 inch (10 mil). JLC system library uuid = `0819f05c4eef4c71ace90d822a990e87`.

### Driving modal dialogs via the DOM (critical)
- There is **no screenshot API** in `easyeda-api`. To observe or operate UI state, inspect/click the DOM. Several calls open a modal and return `true` *without applying* until a button is clicked.
- **Schematic→PCB import:** `pcb_Document.importChanges(schUuid)` returns `true` but leaves the PCB with **0 components** until you click the **"Apply Changes"** button of the PCB-Comparison dialog: `[...document.querySelectorAll("button")].find(b=>b.textContent.trim()==="Apply Changes").click()`. Confirm with `pcb_PrimitiveComponent.getAllPrimitiveId()`.
- **Autorouting:** there is no PCB autoroute API (`SCH_Document.autoRouting` is schematic-only). Click the `Route` header `<span>`, then the `Auto Routing...` menu item, then the dialog's **`Run`** button. Treat 100% completion as `pcb_Drc.check` reporting **0 Connection Errors**. Do NOT click the autorouter's **Cancel** after it finishes — the routes survive but it throws "指定的主题消息…没有相关订阅"; just let the dialog close.
- **Detecting autoroute completion:** the "Auto routing completed!" DOM text is unreliable (sometimes never findable). Poll `pcb_PrimitiveLine.getAllPrimitiveId(undefined,1/2,false).length` + via count every ~12 s and treat **two consecutive identical non-zero readings as done**. Counts can transiently spike high, drop, or even read `0 0 0` mid-run (optimization passes rip and redo) — never conclude from a single read. Keep each in-page wait ≤ ~15–20 s: the bridge kills requests at 30 s, and an in-page `setTimeout` loop longer than that times out the call (the orphan keeps running harmlessly, but you lose its result).
- Confirming any of these workflow dialogs is never the same as authorizing a final JLCPCB purchase.
- **`Apply Changes` can silently reset ALL PCB component positions, even when you only wanted to fix an unrelated sync issue.** Re-running `pcb_Document.importChanges(schUuid)` + clicking `Apply Changes` — for example, as an attempted fix for a persistent DRC `Netlist Error` — is not always an incremental diff; it can re-drop every component back into the default post-import negative-Y dump, discarding all careful placement/rotation work even though the schematic itself was never touched. **Before calling `importChanges` a second time on an already-placed board, record every component's `(designator, x, y, rotation)` first** (a simple `getAllPrimitiveId()` → `get()` → map loop) so a full reposition pass is a matter of replaying recorded coordinates rather than re-deriving the layout from scratch. If positions do get wiped, mounting-hole pads and any `pcb_PrimitivePad`/`pcb_PrimitiveString` objects you created directly (not schematic-linked) are unaffected and survive.

### Bridge / session lifecycle (reloads, hangs, restarts)
- **`dmt_Project.createProject(name)` RELOADS the EDA window**: the bridge `windowId` changes, the in-flight `/execute` fails with "No EDA window connected", and anything after it in that request is lost. Fire `createProject` alone, re-poll `GET /eda-windows` until `count==1`, then verify with `getCurrentProjectInfo()` before retrying — the first attempt may have succeeded even though it "failed". A new project comes with `Board1` = `schematic1` + `PCB1` pre-created; no `createSchematic`/`createPcb` needed.
- **Mid-session window reloads do NOT lose uncommitted edits** — after a reconnect (new `windowId`), re-read the doc: placed components/wires from before the reload are still there. But a combined big call (e.g. wire-delete + component-delete in one `/execute`) can throw `获取所有器件失败` and trigger the reload — split bulk deletes into separate calls.
- **`getAll()` immediately after `create()`/`delete()` can be STALE** (returns the pre-edit count). Re-read once in a fresh call before concluding an edit failed.
- **"Cannot read properties of null (reading 'map')"** on any `pcb_*` call = broken doc state (common after autoroute, importChanges, or idle gaps). Recover with `openDocument(schUuid)` → wait ~1.5 s → `openDocument(pcbUuid)` → wait ~2 s. Edits survive.
- **Export subsystem can wedge**: `getGerberFile`/`getBomFile`/`getPickAndPlaceFile` return `{success:true, result:null}` repeatedly (or time out) after heavy reimport/DRC/route cycles. First try the reopen-SCH→PCB cycle + `save()`; if exports still return null, **only a full EasyEDA Pro restart cures it** (same as the copper-no-fill hang, which also hits FRESH projects after window reloads — not just corrupted docs).
- **The agent can restart EasyEDA autonomously on macOS**: save all docs, `osascript -e 'quit app "EasyEDA-Pro"'`, `open -a EasyEDA-Pro`, poll `/eda-windows` until `count==1`. The extension auto-reconnects and the last project reopens — **but sometimes only after the app is foregrounded**: if the count stays 0 for minutes, `osascript -e 'tell application "EasyEDA-Pro" to activate'` (or the user opening the project) unsticks it. If activation + relaunch still leaves 0 windows for 10+ minutes, **force-quit and relaunch**: `pkill -f "EasyEDA-Pro.app/Contents/MacOS"` → `open -a EasyEDA-Pro` (a soft quit can leave a zombie main process that blocks the extension). `pcb_Document.save()` returning `false` right after a successful save just means "no changes" — not a failure.
- **`importChanges` can wedge into a "diff sees almost nothing" state**: Apply Changes lands only 1-2 components (e.g. just the headers) no matter how many the schematic has, the dialog shows a single stale row, and re-saving the schematic, reopening docs, or even DELETING and recreating the PCB does NOT fix it — the stale comparison model lives at app level. **Cure = full EasyEDA restart**, after which the identical importChanges call lands everything. Also: `dmt_Pcb.createPcb(boardName)` builds a bare document — no board outline, no title silk — recreate both (outline `["R",0,H,W,H,0,r]` on layer 11; strings with the family's fontSize/strokeWidth/align).

### Connectivity (net-named wires)
- Connect a pin by drawing a **net-named wire from its endpoint**: read pins with `sch_PrimitiveComponent.getAllPinsByPrimitiveId(pid)` (`getState_X/Y/PinNumber/PinName`), then `sch_PrimitiveWire.create([x1,y1,x2,y2], "NETNAME")` — flat coordinate array, NOT nested `[[x,y],…]`. Same net name on separate stubs ties them; wires need not touch. `createNetFlag` placed coincident on a pin did NOT reliably show in the netlist — prefer net-named wires.
- Verify connectivity via `sch_ManufactureData.getNetlistFile("name","PADS")` then `await file.text()` (the bare `sch_Netlist.getNetlist()` returned empty/`i is not iterable` in-bridge). A net with one pin in that output is an unconnected pin.

### Board outline / placement / DRC
- Board outline: `eda.pcb_MathPolygon.createPolygon([0,0,"L",w,0,w,h,0,h,0,0])` → `eda.pcb_PrimitivePolyline.create("", 11, poly, 10, false)` (layer 11). One closed polyline, not four lines.
- **Slots, notches, and concave (凹) outlines:** an internal cutout (e.g. an FPC pass-through slot) = a second closed polyline on layer 11 *inside* the outline. To convert a slot into an **edge notch** (open to the board edge), rebuild the outline polyline itself with the notch in its path. Rounded-rect corners use `"ARC",-90` at each **convex** corner when traversing clockwise (screen coords, −y down); **concave corners (inside a notch) use `"ARC",+90`**. Example notch segment in the top edge: `...,"L",1810,0,"ARC",-90,1850,-40,"L",1850,-160,"ARC",90,1890,-200,"L",2834,-200,"ARC",90,2874,-160,"L",2874,-40,"ARC",-90,2914,0,"L",...`. After any outline change: stale pour fill throws `Board Outline to Copper Region(Filled)` (fix = Rebuild All, no reroute), and vias/tracks that were legal near the old edge may now violate — delete offending vias by coordinate window, don't reroute unless tracks are hit. Keep ≥ ~2–3 mm web between a closed slot and the board edge, or go full notch.
- **Layer-11 polylines expose NO geometry getters at runtime** (`getState_Line`/`Polyline`/`Points` all absent), so you cannot identify "the slot" vs "the outline" by coordinates after the fact. Track the outline's primitive ID from creation; to replace a slot/notch, delete **all** layer-11 pids and recreate outline + cutouts in one pass (a coordinate-filter delete silently matches nothing).
- **`lib_Device.getByLcscIds([...])` returns results sorted by LCSC code, NOT input order.** Zipping results to your input array by index silently assigns wrong devices (a battery connector became a 100 Ω resistor this way). Always map by each result's own `lcscId`/`supplierId` field.
- After import, components land spread across **negative-Y**; reposition each with `comp.toAsync().setState_X/Y/Rotation(...); await done()`. A ~390mil(x)/340mil(y) grid keeps small SMD/SOP/SOT/TQFP parts clearance-clean.
- **Edge connectors (USB at the board boundary):** read the connector's pads (`getAllPinsByPrimitiveId`) to find the mouth = the side OPPOSITE the dense signal-pad row. **Do not guess the rotation from this rule alone — verify it empirically before wiring/routing anything against it.** Place the part at a scratch position with a candidate rotation, re-read its pads, and check which side the dense signal-pad row now falls on relative to the part's other features (e.g. the shield/mounting-tab pads): if the signal row is on the *low*-coordinate side of the axis facing the intended board edge, the mouth (opposite side) faces *out* — correct; if the signal row is on the *high*-coordinate side, the mouth faces *into* the board — wrong, flip the rotation by 180° (e.g. `90`↔`270`) and re-check. This exact mistake (mouth facing into the board, caught only after the user visually inspected the board) happened once in this project even though the general "mouth = opposite the dense row" rule was already known — the failure mode was applying it without re-verifying the resulting pad layout after picking a specific rotation value. Once confirmed, set the origin so the front pads sit ~50mil inside the outline and the metal shell overhangs the edge. After moving any routed component, **rip up all tracks+vias first** (`pcb_PrimitiveLine.getAllPrimitiveId(undefined,1/2,false)` + `pcb_PrimitiveVia.getAllPrimitiveId()`, then `delete`) and re-autoroute, else stale tracks dangle. If a swapped footprint has identical pad geometry and you restore the same position, existing routes survive and no reroute is needed.
- `pcb_Drc.check(false,false,true)` returns a verbose error array; categorize by `e.name` (`Clearance Error`, `Connection Error`, `Netlist Error`). 0 categories = clean. Treat DRC success as empty categories, not merely "no fatal exception". If only a `Netlist Error` remains, copper passed but schematic/PCB sync is unresolved (see floating-stub note in Workflow step 4) — say so explicitly; distinguish PCB manufacturing verification from schematic-source verification.
- **Reading DRC error details:** each leaf item's `obj1`/`obj2` carry a `suffix` like `"(IO13): J6_7"` or `"(GND): e345"` (net, designator_pin, or `eNNN` primitive suffix) — this identifies the exact colliding pads/tracks without guessing from coordinates. `pos.x/y` are in **0.01-inch units — multiply by 10 for mil**. Dedup by `(category, suffix1, suffix2)` when one physical conflict spams multiple leaf items.
- **When a connector doesn't fit the top side, move it to the BOTTOM layer** (`setState_Layer(2)`) instead of squeezing: measure the corridor first (neighbor pad-row extents + 2×12 mil clearance vs the part's pad-bbox width) and if it's short by any margin, a bottom-center placement typically routes clean with zero other part moves. Verify orientation empirically after flipping: dump the part's pads filtered by `getState_Layer()===2` and check which side the signal row landed on — bottom-layer mirroring plus rotation is NOT intuitive (for a microSD socket, rot 0 vs 180 flips which board edge the card inserts from). Pin numbers and nets survive the flip. A silk-overlap checker will then report a false "designator over part" hit for top-silk text inside the bottom part's bbox — opposite layers, no real conflict, accept it.
- **Determining a socket/connector's insertion direction from its footprint:** signal-pad row position alone is ambiguous (microSD: 9 pads are at the REAR, opposite the card opening — TF-01A C91145 verified). Get the datasheet: `https://www.lcsc.com/datasheet/Cxxxx.pdf` returns an HTML wrapper — curl it and grep out the real `https://datasheet.lcsc.com/datasheet/pdf/….pdf` URL, download, and read the mechanical drawing. (`lib_Footprint.getRenderImage` returns null and `lib_Footprint.get` 500s in the current bridge — don't bother.) `comp.getState_Footprint()` gives the footprint's `{libraryUuid, uuid, name}` for identification.
- `dmt_EditorControl.zoomToRegion(...)` does NOT affect `getCurrentRenderedAreaImage()` — the capture always renders the whole document. Crop the full render offline (sips/PIL) to inspect a region. The **3D view is also not capturable**: clicking the "3D" toolbar button opens a separate canvas and `getCurrentRenderedAreaImage()` keeps returning the 2D view — for a real 3D render, ask the user for a manual screenshot (don't keep a stale 3D image in a repo; a current 2D top view beats an outdated 3D one).
- **When re-wiring an IC's schematic stubs, map nets by PIN NAME, not pin number** — library symbols use vendor names (`SD_MODE#`, `GAIN_SLOT`, `LRCLK`, duplicate `VDD`/`GND`/`N.C.` pins), and numbering varies between symbol variants. Read `getState_PinName()` per pin, build the net map keyed on names (with designator-specific overrides for numbered passives), and leave intentionally-floating pins (e.g. MAX98357A GAIN for 9 dB) without stubs.
- **Schematic DOC uuid ≠ PAGE uuid:** `getAllBoardsInfo`/`getAllSchematicsInfo` return the schematic *document* uuid, but `openDocument` only accepts the schematic *page* uuid (`board.schematic.page[0].uuid`); PCB uuids open directly. **A failed `openDocument` returns undefined and silently leaves the previous document open** — the next `getAll()` then reads the WRONG doc and looks plausible. Always verify the openDocument return value (`"uuid@projectUuid"`) before trusting any read. `importChanges` accepts the DOC uuid.
- **`createSchematic()`/`createPcb(name)` can silently fail to register a new board** (returns a uuid but no board appears, even after an app restart). Reliable new-board recipe: `dmt_Board.copyBoard("ExistingBoard","NewName")` (arrives as `…_1` — rename board + both docs), then strip the copied schematic (delete wires until 0, delete unwanted components), rip all copper, and build the new circuit — outline, pour definitions, and title silk survive the copy for free.
- **After ANY component swap that involved deleting/re-stubbing schematic wires, run a pads-per-net audit** (`pcb_PrimitivePad.getAll()` → count by `getState_Net()`, compare to the design's expected per-net pin counts). Net-stub auto-merge can collapse a whole board into 2-3 mega-nets (seen: 36 WS2812s with every DO+DI on one net and every VDD absorbed into GND) while **DRC stays 0 for multiple sessions** — schematic and PCB were consistently wrong, and only the count audit caught it.
- **Touch electrodes via `pcb_PrimitiveFill.create(layer, complexPolygon, net, fillMode=0, lineWidth=0, lock=false)`** (arg order matters — net is THIRD; wrong order throws "无法创建填充图元"). A fill overlapping a same-net component pad IS the connection — give each electrode a single-pin net (header → series R → `PADn`, fill overlaps R's pad-2) so nothing needs manual routing. Add `pcb_PrimitiveRegion.create(2, poly, [7], name, 5, false)` no-pour windows on the bottom layer under each electrode for sensitivity. ESP32-S3: IO1-9 double as TOUCH1-9 and ADC1_CH0-8.
- EasyEDA enum globals may not exist in the bridge context. Use numeric constants: Top Layer `1`, Bottom Layer `2`, Top Silkscreen `3`, Board Outline `11`, normal via type `0`, centered string alignment `5`.
- Use `PCB_PrimitiveString` on Top Silkscreen layer id `3` for requested board text; center-align when available, then rerun DRC. Validate `fontFamily` against `sys_FontManager.getFontsList()` first (`"default"` always works) — passing an unlisted font throws.
- **`getAllPinsByPrimitiveId` is SCHEMATIC-only** — calling it on `pcb_PrimitiveComponent` HTTP-500s. On the PCB, dump pads via `pcb_PrimitivePad.getAll()` and match `id.startsWith(componentPid + "e")` (component sub-primitives share the `<pid>eNN` prefix). The same prefix trick finds a component's `pcb_PrimitiveAttribute` entries (designator-hide: prefix-filter `getAllPrimitiveId()`, then `getState_Key()==="Designator"` → `setState_ValueVisible(false)` in chunks of ~25/call).
- **`dmt_Project.createProject(name)` can succeed WITHOUT switching to the new project** (no window reload; `getCurrentProjectInfo()` still shows the old project). Always verify and call `dmt_Project.openProject(uuid)` explicitly — the uuid comes back from createProject.
- **An app restart can reopen a DIFFERENT project than the one you were editing** (whatever was last active wins). After any restart/reconnect: `getCurrentProjectInfo()` FIRST; if wrong, `dmt_Project.openProject(uuid)` (works, triggers a reload — wait ~10s and re-verify). Opening a document belonging to a non-loaded project returns undefined and leaves the previous doc open — combined with the wrong-project trap this silently reads/edits the wrong board.
- **`pcb_PrimitiveString.create(...)`'s rotation/angle argument can be silently ignored** (text renders horizontal despite angle=90). Verify silk text orientation in a rendered capture; if it comes out wrong, reposition to a spot where horizontal fits rather than fighting the arg.
- **Mounting holes near parts: check the SCREW HEAD, not just the pad.** An M2.5 head is ~Ø4.5 mm (r ≈ 88 mil) — a hole whose NPTH pad clears a switch body by DRC can still put the screw head on top of the part. Keep head-radius clearance to component bodies (adjacent-face parts are exempt).
- **Some manager classes (`PCB_PrimitiveString`, `PCB_PrimitiveAttribute`, …) have zero methods listed in the offline `references/classes/*.md` docs, but the methods exist and work at runtime.** Do not conclude an API "doesn't exist" from an empty docs page alone — check `Object.getOwnPropertyNames(Object.getPrototypeOf(eda.pcb_PrimitiveString))` (or the relevant `eda.xxx`) in a bridge call first; if `create`/`modify`/`get`/`delete` show up, the class is usable even though undocumented. Infer the parameter order from the matching `IPCB_*`/`ISCH_*` **interface's constructor** signature (which usually *is* documented) — the manager class's `create()` typically mirrors it positionally.

### Order data / manufacturing files
- `getBomFile`/netlist read the **saved** document — call `pcb_Document.save()` *before* regenerating, or the export shows stale field values.
- `placePcbOrder()`/`placeComponentsOrder()`/`placeSmtComponentsOrder()` are interactive-only and the harness safety classifier **blocks** them as real order transactions. For "order data + quote" scope, generate the files instead and let the human upload to JLCPCB.
- `getBomFile`/`getPickAndPlaceFile`/`getGerberFile` return browser `File` objects: `await f.arrayBuffer()`, chunk-base64 it, return over the bridge (large results auto-spill to a tool-result file — decode that with a Python helper). Validate the Gerber zip with `unzip -t`; if the file name lacks `.zip`, add it.
- **The BOM/PnP export wedge can SURVIVE an app restart** (getBomFile/getPickAndPlaceFile kept 500ing while getGerberFile and sys_FileManager.getProjectFile worked fine in the same session). When only BOM/PnP are stuck and the change is small, **patch the previous xlsx directly with openpyxl** instead of fighting the API: BOM = append rows (Supplier Part / Manufacturer Part / Footprint / Designator / Quantity); PnP = append or edit rows with `Mid X/Y = Ref X/Y = component_mil × 0.0254` formatted `"33.02mm"`, `Layer` T/B, `Rotation`, `SMD` No for THT. The Gerber is the authoritative geometry — a hand-patched BOM/PnP whose values match the live design is production-safe; still regenerate properly once exports recover.
- **Exporting the EasyEDA project source itself (for GitHub publication etc.): `sys_FileManager.getProjectFile("name")`** returns an `.epro`/`.epro2` File (a zip: `<project>.epru` + preview webp + `project2.json`) that EasyEDA Pro reopens via File → Open. `dmt_Project.getProjectFile`/`getProjectFileByProjectUuid` appear in the offline docs but are **not functions in the current build** — the working method lives on `sys_FileManager`.
- **Current EasyEDA exports BOM and Pick-and-Place as `.xlsx`, not CSV** — `getBomFile()` returns `Export_BOM.xlsx`, `getPickAndPlaceFile()` returns a file named `Pick_Place` whose bytes are an `.xlsx` (zip starting `PK\x03\x04`). Save with `.xlsx` and verify content by reading `xl/sharedStrings.xml` from the zip and grepping for designators / new+old C-numbers (the old `'csv'` format arg and the "BOM CSV is UTF-16" rule are legacy — handle whichever the bridge returns). Gerber is still a `.zip`.

### Editing/swapping a placed component (delete + recreate + re-import)
- To change a component's part/footprint (e.g. a wrong-shape or wrong-height header), delete it in the schematic, create the replacement, re-wire its pins, save, then re-import to PCB (Apply Changes) and reposition. Gotchas seen:
  - A single call doing `create` + `getAllPinsByPrimitiveId` can hit the 30s bridge timeout, and the bridge **retries** — leaving duplicate stray components with `null` designator. Split into create-then-read calls; afterward list components and delete any `null`-designator strays.
  - Old stub wires left after the delete become floating named-net segments → `Netlist Error`. Delete them (see step 4) before/after re-import.
  - **A batch that times out at 30s may keep executing in the browser after the bridge reports the error to you.** If you then issue a *new* call that creates the same or overlapping items (e.g. resuming a large placement loop in smaller chunks after a timeout), the orphaned original run and your new run can both land, producing duplicates that this time have **valid, non-null designators** (both copies got the same `modify()` call), not just the null-designator case above. After any batch that either timed out or that follows one that did, re-fetch all components, group by `Designator`, and for every designator with `count > 1`, keep only the primitive ID you can positively attribute to a call you know completed cleanly (e.g. the IDs returned directly by your most recent, fully-successful chunk) and delete the rest — do not assume "first" or "last" in listing order is the right one to keep.

## Pre-Wiring Design Review (new designs — run BEFORE creating stub wires)

The cheapest moment to fix a schematic-level mistake is after placing components but before wiring. On a from-scratch design, run independent datasheet-grounded reviews (parallel subagents work well: one per domain — MCU pins, audio, keyboard/IO, net-count arithmetic — then adversarially verify each major finding). Every one of these caught a real defect on a design that "looked done":

- **Mode-select pins use ABSOLUTE voltage thresholds, not "pullup = mode X" folklore.** MAX98357A SD_MODE has an internal ~100 k pulldown and trips at 0.16/0.77/1.4 V: a 100 k pullup to 3.3 V lands at ~1.6 V = **LEFT-channel mode**, NOT the commonly-assumed (L+R)/2 — that needs ~634 k (datasheet Table 6). Left mode is fine for mono IF firmware puts samples in the left I2S slot; document the contract either way. Compute the divider against the internal pull before trusting any strap resistor.
- **Heavy analog loads do not belong on a dev-module's 3V3 LDO.** A speaker amp (~240 mA avg, ~0.4 A peaks at 3.3 V/8 Ω BTL) plus ESP32 WiFi TX bursts (~350 mA) exceeds the XIAO's ~700 mA regulator → brownout. Move amp VDD to VBAT: MAX98357A VDD range is 2.5–5.5 V and its digital inputs have FIXED thresholds (VIH 1.3 V), so 3.3 V logic drives it fine at any VDD. Move its decoupling caps to the same rail. (Mics are the opposite: MSM261-class VDD max is 3.6 V — never VBAT.)
- **Multi-drop clock nets (>3 loads spread across the board) need a damped branch, defined in the SCHEMATIC before autoroute** — the autorouter will produce an arbitrary star topology. Recipe: keep the fast receiver (LCD SCL) on a short 2–3-load net, and feed the slow fan-out (five 74HC165 CLKs) through a series 33 Ω (Basic `C25105`) that creates a separate net (e.g. `KB_SCK`). One resistor, no firmware cost.
- **Strapping pins that are Hi-Z at reset must not float CMOS inputs.** ESP32-S3 GPIO3 (XIAO D2) is the JTAG-source strap with NO internal pull; five paralleled 74HC165 SH/LD# inputs on it floated from power-on until app code ran. Add a 10 k pull to the idle-state level (high = shift mode). GPIO43/44 (XIAO D6/D7) are UART0 — repurposing them for I2S is fine (boot log on DIN is inaudible: amp mutes without BCLK; mic SD tristates without SCK) but move the console to USB-Serial-JTAG in sdkconfig.
- **Read the mic/sensor datasheet's "required externals" list literally.** MSM261S4030H0R requires a 100 k pulldown on SD (line floats every unused I2S slot) and 100 nF + 10 µF at VDD — neither is in the EasyEDA symbol's orbit, both are review catches.
- **Daisy-chained shift registers: tie the LAST chip's SER to the released-key level (3V3 for active-low keys), not GND** — otherwise any firmware over-read fabricates phantom keypresses instead of harmless "released" padding.
- **RC reset on an SPI display (10 k + 1 µF on ST7789 RESX) is valid** (τ=10 ms, reset-low ≫ 10 µs min) and frees a GPIO, but firmware must wait ~135 ms after power before LCD init, and SWRESET (0x01) is the only recovery from a rail dip — note both in the project docs.

For the wiring itself at scale (100+ components): dump all pins, build the netmap OFFLINE keyed by **pin NAME** (not number — symbol pin numbering vs function is where traps live), generate stubs offline with a collision check (length 5 < pin pitch 10, direction perpendicular-outward from centroid, tolerance ~3), create in batches of ~8/call, save, then diff the PADS netlist export against the netmap **per-net pin set** (not just counts). A 111-component / 329-stub / 66-net board landed 100% netlist-clean on the first pass this way.

## Multi-Chip 74HC165 Keyboard Chain (full-key-rollover QWERTY)

Proven 40-key recipe (5× SN74HC165DR `C61060`, one input per key → no matrix, no diodes, no ghosting):

- **EasyEDA symbol pin map — mind the package split**: inputs are A=11, B=12, C=13, D=14, **E=3, F=4, G=5, H=6** (A–D and E–H sit on opposite package sides; wiring 3-6 as A-D is the classic trap). 1=SH/LD#, 2=CLK, 7=QH# (NC), 8=GND, 9=QH, 10=SER, 15=CLKINH→GND, 16=VCC.
- Chain: first chip QH → MCU MISO; each SER ← next chip's QH; **last SER → 3V3**. All SH/LD# common (latch GPIO + 10 k pullup), all CLK on the damped `KB_SCK` branch (see review section). Keys: switch pin1 → KEYn + 10 k pullup to 3V3, pin4 → GND (diagonal rule); chip N's A..H = keys 8N-7..8N in order.
- Sharing SCK with a write-only SPI LCD is safe: LCD CS idles high during scans, HC165 shifts garbage that the next latch discards, and the sole MISO driver is chip 1's QH. Firmware contract: SPI **mode 0** (mode 1 drops bit H), ≤10 MHz on the keyboard device (74HC165 fmax ~20–25 MHz at 3.3 V), latch pulse + exact 40-bit read inside `spi_device_acquire_bus()` so LCD transfers can't clock the chain mid-read.
- Layout: pullups fit as 4×2 blocks under each chip; put each chip's 100 nF in the **inter-chip gaps**, never in the band directly below the pad rows — caps there choke the escape corridor (signature: autorouter leaves 1 KEY net unrouted + paired Hole-to-Hole via errors near the chip row, every pass). Moving 5 caps into the gaps + full rip gave a clean second pass.

## JLCPCB Stock Realities (live — re-verify every time)

- **Audit EVERY assembled part's stock, not just the row JLC flagged.** Standard passives (10k/100k 0402, 100nF/1µF/10µF MLCC) are JLC **Basic** and effectively always in stock; odd/precise values are often **Extended** with thin stock (a 191Ω 0402 `C25085` showed only 3 in stock and failed a 20-qty order). For a non-critical role (MOSFET gate series R, pull-up) swap the odd value to the nearest **Basic** value (e.g. 191Ω→100Ω `C25076`) — same footprint ⇒ supplier-only swap, no reroute.
- **Seeed XIAO / Raspberry Pi Pico / bare ESP-WROOM dev-modules are consign-only at JLC: 0 assembly stock, and changing the LCSC part number does NOT fix it** — every listing of the same module draws the same empty inventory. Confirmed all 0-stock: XIAO ESP32-S3 `C20467913`, `C9900154951` ("XIAO ESP32S3", JLCPCB-Assembly listing), XIAO ESP32-C3 `C19189385`. The user must **consign** the module (ship their own) or hand-solder. Keep it in the BOM with `addIntoBom=true` and a correct C-number so it appears as a shortfall/consign line, not "No Part Selected".
- **`C9900…`-prefixed parts** are EasyEDA-internal / "JLCPCB Assembly" listings — some resolve for consignment, others show "No Part Selected/unmatched" in the PCBA quote. Prefer a real-manufacturer C-number when one exists.
- **12×12mm tactile switches (THT and SMD) are all consign-only/0-stock at JLC.** Don't promise large 12mm buttons as turn-key SMT. In-stock tacts are small 6–7.5mm SMD (e.g. GT-TC155C `C5155558`); for a large feel use 7.5mm SMD + oversized button caps in the enclosure (PCB switch centers unchanged ⇒ enclosure cutouts still align).
- The EasyEDA search API does NOT return real stock — verify each candidate via `WebFetch https://jlcpcb.com/partdetail/Cxxxx` ("In Stock: N", Basic/Extended). LCSC pages usually don't render stock to WebFetch; the JLC partdetail page does.
- A footprint change (THT→SMD, different lands) is NOT a supplier-only swap: delete+recreate in schematic, re-stub nets, re-import (Apply Changes), reposition, then full reroute. Only same-land swaps are supplier-field-only.
- **Even "always in stock" Basic staples go to zero — verify every time.** The definitive 10 kΩ 0402 Basic (`C25744`, UNI-ROYAL 0402WGF1002TCE, normally ~1 M stock) hit 0 stock / "26 shortfall" on a real order, and **no Basic 10 k 0402 existed at all that day**. Good Extended fallbacks found via the parts API: PANASONIC `ERJ2RKF1002X` **C191123** (±1 %, ~93 k), BOURNS `CR0402-FX-1002GLF` C202396 (~27 k), HKR `RCA0210KJLF` C22356213 (±5 %, ~150 k), Yageo thin-film `RT0402BRD0710KL` C190095 (±0.1 %, ~640 k).
- **Bulk stock search without WebFetch:** `POST https://jlcpcb.com/api/overseas-pcb-order/v1/shoppingCart/smtGood/selectSmtComponentList` with `{"currentPage":1,"pageSize":50,"keyword":"10K 0402","componentLibraryType":"base"}` (omit `componentLibraryType` to include Extended). Read `data.componentPageInfo.list[]` → `componentCode`, `stockCount`, `componentLibraryType` (`base`/`expand`), `describe`. Much faster and more reliable than scraping partdetail pages one by one.
- **4-pin tactile switches with uncertain terminal pairing: wire DIAGONALLY.** Datasheets pair the two contacts either by side (1,3 | 2,4) or by row (1,2 | 3,4), and the EasyEDA symbol's pin numbering doesn't reliably reveal which. Wiring signal to one pin and GND to the diagonally opposite pin (e.g. 1 and 4) is correct under BOTH schemes — a diagonal internal pairing doesn't occur in practice. The two unwired pads still get soldered (mechanical only). Wiring both same-side pairs without checking risks a hard short through the switch.
- **Parts the user sources themselves (displays, batteries, speakers) can simply be LEFT OUT of the BOM**: place a component for mechanical reference if useful (its pads carry no nets → no DRC/routing impact; note stale pour fill still needs Rebuild All after moving it), or delete it and keep only a silkscreen outline + dimension text as the mounting guide. Both are cleaner than a "No Part Selected" row at the quote.
- **When the exact C-number is 0-stock, search the parts API by FAMILY PREFIX (e.g. `MLX90393`, `VL53L1`, `BMP58`) — the same die is usually listed under several C-numbers.** Resolution ladder, best first: (1) **packing-suffix sibling** — trailing `-RE`/`-SP`/`-TR`/`-TU` on ST/Melexis/Bosch parts is reel-vs-tray packaging, identical silicon (MLX90393ELW-ABA-011-**SP** C1526586 0-stock → **-RE** C2654971 in stock; keep any config code like `-ABA-011` identical — that one changes I2C address/firmware). (2) **marketing name vs official order code** — "VL53L1X" resolves to a 0-stock listing while **VL53L1CXV0FY/1 (C190004)** is the same part with 5k+ stock; the EasyEDA-lib `.1` supplierId tends to resolve to the 0-stock listing. (3) **pin-compatible family sibling** — e.g. BMP581 (all listings 0-stock) → **BMP580 C22391138**: identical LGA-10 2×2 footprint/pinout, same Bosch bmp5 driver, but piezo-resistive vs capacitive = lower accuracy (±6 Pa vs ±0.4 Pa rel) — state the spec tradeoff explicitly and let it be reversible (supplier-fields-only). Beware LOOK-ALIKE siblings with different packages: BMP585 is LGA-9 3.3×3.3 (NOT compatible); VL53L3CX/L4CX are 4.4×2.4 (vs L1X 4.9×2.5). Verify the listed package string matches before proposing.
- **If the swapped part's NAME is printed on the board silk (title like "BMP581 x9 SPI Shield"), update the silkscreen string in the same pass** (`pcb_PrimitiveString` → `getState_Text()` regex → `toAsync().setState_Text(...)`) — a silk/BOM mismatch survives to the physical board.
- **I2S MEMS microphones: the MEMSensing MSM261 family is mostly 0-stock at JLC** (MSM261S4030H0R `C2840615` = 0-stock consign; its JLC-lib footprint `MIC-SMD_8P-L4.0-W3.0-P1.00-BR` is fine). In-stock I2S alternative: TDK **ICS-43434 `C5656610`** (~12 k). The in-stock MSM261D* variants and MSM381A*/MSM421A* lines are different interfaces (PDM / analog) — check the interface column, not just the family name. **MSM261S4030H0R is a TOP-port mic**: no PCB acoustic hole, normal top-side SMT, mount it on the board face that faces the enclosure's sound opening; wiring: CHIPEN→3V3, L/R→GND = data in the LEFT I2S slot.
- **A part the user supplies from their own stock ("自分の在庫使います") stays IN the BOM with its real C-number** — it shows as a 0-stock/consign line at the quote, which is correct: JLC assembles consigned parts on Standard PCBA. Don't delete it like a user-mounted display; the assembler needs the BOM row + PnP entry.

## Rip-up & Reroute (whenever a routed part moves/rotates/swaps)

- **Always loop-delete tracks/vias/poured until the count is verified `0` BEFORE auto-routing.** A single `getAllPrimitiveId(...,1/2,false)`+delete pass reliably leaves leftovers (seen repeatedly: pass-0 deletes ~480, pass-1 still finds 8–16 more, pass-2 reaches 0). Routing on a partially-routed board yields junk (random GND/3V3/BTN connection errors, stray clearance errors). Loop {delete layer-1 + layer-2 lines + `pcb_PrimitiveVia` + `pcb_PrimitivePoured`; re-read all four counts} until `==0`, THEN Run autorouting. (User-corrected lesson.)
- A clean full rip + a single autoroute pass routes dense areas that incremental passes and hand-routing cannot. Do NOT hand-route a congested row (e.g. a 3V3 bus threading between alternating BTN pads 34mil apart hits clearance every time and made it *worse*). Trust the clean autoroute.
- After autorouting, the PCB doc often drops into a broken state where `getAllPrimitiveId` throws **"Cannot read properties of null (reading 'map')"** (autorouter dialog/canvas leftover). Recover — routes survive — with `openDocument(<schematicUuid>)` → wait ~1.5s → `openDocument(<pcbUuid>)` → wait ~2s, then re-query. Do NOT click the autorouter Cancel.
- **Manually placed stitching vias should be added *after* the main autoroute, and only at candidate points you've checked against existing track geometry (not just component/hole keepouts).** Component-only collision checks (bounding boxes + hole keepouts) still let plenty of candidates land on top of the router's own traces. Compute point-to-segment distance against every existing `pcb_PrimitiveLine` on both layers (`x1,y1,x2,y2` from `getState_StartX/Y`/`getState_EndX/Y`) and reject any candidate closer than track-width/2 + via-radius + clearance.
- **Proven offline-precompute recipe for a full-board GND stitching grid (330+ vias, zero DRC failures on the first Rebuild):** extract all pads (`x, y, max(shape w,h), hole dia, net`), all layer-1/2 lines, and existing vias over the bridge; filter a 250 mil grid + a 250 mil half-offset (staggered) infill in Python with these rejection radii — pad: `pad_half + via_r + 20` (relax to `+15` for GND pads), track: `w/2 + via_r + 20` (GND tracks `+12`), THT/NPTH hole-to-hole: `hole_r + via_hole_r + 45`, board edge: 60 mil, plus exclusion windows for slots/notches (outline + 60). The extra ~20 mil over bare clearance is **pour margin** — it keeps every via inside the rebuilt copper, so none land in pour voids and the delete-failed-vias/re-rebuild loop is skipped entirely. Create with `pcb_PrimitiveVia.create("GND", x, y, 12 /*HOLE*/, 24 /*DIA*/)` — **hole comes before diameter** — in batches of ~30/call, then Rebuild All → DRC. If a routed part later moves and you loop-rip everything, the rip deletes stitching vias too — just re-run the same precompute+create after the reroute (~30 s).
- **After replacing components via schematic delete+recreate + Apply Changes, the new components' silkscreen `Designator` attributes reset to visible** (unchanged components keep their hidden state) — re-hide them (`pcb_PrimitiveAttribute` → `Key==="Designator"` → `setState_ValueVisible(false)`). Also back up `(designator, x, y, rotation, layer)` for ALL components before every `importChanges`, and restore by designator afterward — include `layer`, since flipped components would otherwise restore to the wrong side.
- **Never bulk-delete vias by `pcb_PrimitiveVia.getAllPrimitiveId(netName)` when cleaning up a mistake — this also deletes legitimate layer-change vias the autorouter placed for that same net**, not just the ones you manually added. Deleting "all GND vias" to undo a bad batch of stitching vias broke real GND traces (dangling stub tracks, a component pin left disconnected) and even produced a schematic/PCB `Netlist Error` that required a full rip-up + reroute (and, in one case, an `importChanges`/`Apply Changes` cycle that reset all component positions — see the EasyEDA API Notes warning on that) to recover from. Always track and delete only the primitive IDs your own `create()` calls returned.

## GND Copper Pour (ベタ)

- Two states: the pour **definition** (`pcb_PrimitivePour` — net+layer+polygon, persists in the saved doc) vs the **filled copper** (`pcb_PrimitivePoured`). A defined-but-unfilled pour has `pcb_PrimitivePoured.getAllPrimitiveId().length == 0` and renders with no ground plane. No fill API exists — rebuild via DOM: Tools → "Copper Manager..." → "Rebuild All" → "Confirm".
- **A handful of GND `Connection Error`s right after autoroute is not a routing failure** — the router sometimes strands a few GND pads (e.g. switch ground pins) that the pour will absorb. Don't hand-patch or re-rip for GND-only errors: create/rebuild the pours + stitching vias first, THEN judge DRC. (Non-GND connection errors still mean unrouted copper — fix those before pouring.)
- Create: `pcb_PrimitivePour.create(net, layer, poly, "solid", preserveSilos=false, name, priority, lineWidth, lock)` (layer numeric 1/2; `preserveSilos=false` drops dead islands).

### Orphan GND pads / floating vias / pour voids (repair playbook)

- **Diagnose by DRC signature.** `Connection Error` on a GND SMD pad or via = it sits in a pour void or a dropped island. First try nudging a floating via toward the nearest **connected** GND via (small steps, re-rebuild, re-DRC). If a via keeps floating after 3+ nudges, or **an orphan-pad error flickers between rebuilds** (connected on one Rebuild All, orphaned on the next — Rebuild All keeps/drops marginal slivers nondeterministically), the copper is marginal by design: stop nudging and shrink the pour clearance rule.
- **Zone clearance rule shrink (the systemic fix):** `const cfg = await eda.pcb_Drc.getCurrentRuleConfiguration(); const t = cfg.config.Spacing["Safe Spacing"].copperThickness1oz.tables["1"].content; for(let i=0;i<7;i++) t[7][i]=0.152; await eda.pcb_Drc.overwriteCurrentRuleConfiguration(cfg.config);` — row index 7 = "Copper/Plane Zone", columns 0-6 = vs Track/SMD Pad/TH Pad/test points/Via/Fill; 0.254→0.152 mm widens every sliver and spoke (JLC can fab 0.127). Pass the INNER `cfg.config` (the full return silently no-ops). Rule APIs can leave DRC returning `null` afterwards ("no subscription" state) — reopen SCH→PCB docs, then Rebuild All → DRC. One rule shrink + one rebuild fixed 4 chronic orphans (2 pads + 2 stuck vias) at once where dozens of via nudges had failed.
- **Fine-pitch LGA corner GND pads (0.5/0.65 mm pitch, e.g. BMP581/BMP580) CANNOT be rescued with a track** — every escape direction is < 12 mil from a neighbor pad; an attempted rescue track just adds Clearance Errors. Pour spokes (via the rule shrink) are the only fix. And when connecting anything to a "nearest via": **filter candidates by `getState_Net()==="GND"`** — a nearest-via list without a net filter will include the autorouter's signal vias (a GND rescue track once landed dead on an SCLK via).
- **Verifying user-added stitching vias** (user says "ビア追加したので確認を"): dump all vias (`total / by-net / no-net counts`), Rebuild All, DRC; for each `Connection Error` via, nudge toward the nearest connected GND via and loop; delete exact-position duplicates (two vias at identical coords = user double-click); a via too close to a signal track throws paired `Track to Via` + `Hole to Track` — relocate it perpendicular to the track to ≥ ~40 mil from the centerline. If `toAsync().setState_X/Y` on a via 500s mid-call, the reliable move is **delete + `pcb_PrimitiveVia.create("GND", x, y, 12, 24, 0)`** (hole before diameter). Note a "failed" (timed-out) bridge call may still have applied its edits — always re-read positions before retrying, or you'll double-apply.
- **If Rebuild All won't fill (`poured` stays 0) it is a stuck session, not a geometry bug — the only reliable fix is a full EasyEDA Pro restart** (reloading the doc does NOT help; this hits FRESH projects too, typically after `createProject`-induced window reloads — see the Bridge/session lifecycle section for the autonomous-restart procedure); after restart Rebuild All fills immediately. Always verify `pcb_PrimitivePoured` count > 0 after rebuild, and re-pour after every reroute. (A clean autoroute may route all GND via tracks, so DRC can read 0 even before pouring — the pour still adds the plane.) Before asking the user to restart, it's worth one retry of Rebuild All after any bridge/EasyEDA reconnect that happens to occur (a disconnect-reconnect cycle has been observed to unstick a session that repeated Rebuild-All clicks alone could not) — but don't go out of your way to force a disconnect just to test this.

## Hardware Bring-up on the Fabricated Board (display colors, audio)

First rule: **confirm which board revision is physically connected before debugging any peripheral.** Read the silkscreen title from the user's photo and diff that revision's schematic deltas against what the firmware assumes. Real case: audio "didn't work" because the connected board was v1 (amp VDD on VBAT, speaker external via connector) while the firmware/docs described v2 (amp on 3V3, different speaker plumbing) — no amount of firmware debugging could have fixed it.

### Wrong / inverted LCD colors (ST7789-class SPI panels)

- **Panels of the same part number vary by batch: some need INVON (invert_color(true)), some INVOFF.** Symptom of the mismatch is a clean photographic negative: red UI elements → cyan, brown → light blue, dark scenes → washed light. (HS20HS072RX 2025.12 batch: needs INVON — an earlier unit worked with INVOFF.) Keep the setting as a one-line BSP flag so the fix is a constant, not a hunt.
- **Diagnose in ONE user round-trip with a 3-row color-bar test**: draw three rows of RED/GREEN/BLUE/WHITE bars — row 1 = normal values (proven-good macro from an app that displayed correctly), row 2 = bitwise-NOT, row 3 = byte-swap removed — and ask which row shows true colors. Trick: for pre-byte-swapped RGB565 values, `~swapped(v) == swapped(~v)`, so plain bitwise NOT of the normal value IS the inverted-color row. Row 2 correct → flip panel inversion; row 3 correct → wire byte order bug; row 1 correct → panel fine, bug is in the data path.
- **Prove the data path separately over serial before blaming the panel**: dump the palette/LUT *source* values (e.g. Doom PLAYPAL index 176 must read (255,0,0)) — if the source and LUT math are provably identical to the known-good app's, the transform is panel-state, full stop.
- If the user misses the N-second diagnostic window, lengthen it and reflash rather than asking them to catch a reboot.

### Silent I2S audio

Bisect firmware-vs-hardware by **instrumenting the firmware chain first** (one-shot serial logs, not per-frame spam): (1) sound-start calls with sample name/volume/rate/length, (2) "first nonzero audio block" from the mixer, (3) any I2S write error. If all three fire cleanly, the data IS on the I2S pins — stop editing code and check hardware in this order:

- **Amp power rail**: an amp on VBAT (correct design for current budget — see the design-review section) is silent on USB-only power unless the module's charger back-feeds the BAT pad; a lit VBAT-powered backlight proves the rail has *some* voltage but not that it's stable under amp load. Connect the battery to make it solid.
- **Speaker presence**: boards with a speaker *connector* (no onboard speaker) obviously need one plugged in — check the user's photo before anything else.
- Legacy game-engine ports may also **hardcode sound off in the core** (esp32-doom: `nosfxparm=true` in d_main.c) and ship data files with sound lumps stripped (doom1-cut.wad) — grep the core for the mute before instrumenting; verify the data file actually contains audio lumps.

### Serial capture on USB-Serial-JTAG during bring-up

- Open the port with `dtr=False, rts=False` **before** `open()` (pyserial: set attributes on an unopened Serial object) or the open itself can reset the target mid-session; only pulse DTR/RTS when you *want* a reset to capture boot logs.
- The host port handle can die with "Device not configured" (Errno 6) when the target resets or re-enumerates mid-read — wait a few seconds, confirm `/dev/cu.usbmodem*` is back, and reopen; the target is usually fine.
- Boot logs are buffered by the USB-JTAG console until a host connects, so a capture started a couple of seconds after reset still sees the full boot.

### Porting legacy C game engines to ESP-IDF v6 (compact pointers)

- IDF v6 compiles C as gnu23: 1990s C (`typedef enum {false,true} boolean`) hard-fails — give those components `-std=gnu17` (later `-std` flags override) plus a broad `-Wno-error=` list; IDF uses plain `-Werror` so even `-Wextra` warnings like missing-field-initializers promote.
- Game data goes in a raw custom partition (convention: type `0x42`, subtype 6) flashed with `esptool write-flash <offset> file`; on ESP32-S3 mmap the whole partition once with `esp_partition_mmap(part, 0, part->size, ESP_PARTITION_MMAP_DATA, ...)` (32 MB data window) — no handle caching needed.
- Do not override libc `access()` on IDF v6 (VFS defines it; multiple-definition link error) — the VFS one returns -1 for unmounted paths, which is the "not found" legacy code wants anyway.
- prboom headers cannot be included after FreeRTOS headers in the same TU (stdbool `false`/`true` macros vs the boolean enum) — order prboom first, or declare the entry point extern.
