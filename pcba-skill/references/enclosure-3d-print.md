# 3D-Printed Enclosure Orders (JLCPCB 3D printing) + Fusion 360 gotchas

- A model submitted for 3D printing must be **ONE connected solid (single shell)**. JLC rejects: "the file contains multiple shells that cannot be automatically merged… one file supports one part/shell." In Fusion verify `body.lumps.count == 1` for every exported body and **gate the STL/STEP export on it**.
- **Coincident-plane unions do NOT merge** — two solids that only touch face-to-face (zero overlapping volume) stay separate lumps ⇒ multiple shells. Make mating features **overlap** (share volume) or remove them. Seen: an alignment tongue/lip that only kissed the lid at the parting plane made `lumps=2`; removing it (relying on corner screw bosses for alignment) fixed it. Build screw bosses to overlap the floor (`cyl` starting at the floor's bottom Z), not sitting on its top face. (Model the case in Fusion via `TemporaryBRepManager` box-booleans, one body per part, and export each body separately with `createSTLExportOptions(body, path)`.)
- **`lumps.count == 1` proves the body is one connected shell — it proves nothing about whether a cut/hole feature actually removed material.** A cut whose extrude direction is wrong just extends into empty space next to the body and silently no-ops: no error, `lumps` stays 1, and the feature shows as a normal (non-suppressed) timeline entry. Treat visual inspection and the lumps count as necessary but not sufficient. **After every cut feature (mounting holes, connector cutouts, pockets), verify with `body.pointContainment(point)`** at a point that should now be empty (expect `2`/Outside) and at a point just outside the cut that should still be solid (expect `0`/Inside) — `1` means exactly on a boundary face/edge. Do this before moving on to the next feature, not just once at the end; a wrong-direction cut compounds badly once later features are built relative to it.

### Fusion 360 scripted modeling — API unit and geometry gotchas

These cost real rework in this project (a 10x oversized case, and two silently-no-op cutouts) and are easy to hit again:

- **The Fusion API's internal length unit is always centimeters, regardless of the document's *display* unit.** `design.unitsManager.defaultLengthUnits` can report `"mm"` while every `adsk.core.Point3D.create(...)`, `ValueInput.createByReal(...)`, and returned `boundingBox` coordinate is still in cm. Passing a millimeter value straight into `createByReal()` makes the model **10x too large** with no error — it will "work" (extrude, boolean, export) and look plausible in a screenshot at the wrong zoom level. Wrap every length constant in a small helper (`def mm(v): return v / 10.0`) and pass `mm(value)` everywhere, or use `design.unitsManager.convert(value, 'mm', unitsManager.internalUnits)` explicitly. **Verify the final size** by converting a `boundingBox` dimension back to mm (`unitsManager.convert(bb.maxPoint.x - bb.minPoint.x, unitsManager.internalUnits, 'mm')`) and comparing to the intended value before exporting — do not trust a screenshot alone to catch a 10x scale error.
- **A single-component "Part Design" document cannot hold a sub-occurrence.** `rootComponent.occurrences.addNewComponent(...)` throws `"パーツ デザイン ドキュメントには1つのコンポーネントのみを含めることができます"` (or the English equivalent) if the active document is that simpler single-body document type. Build directly on `design.rootComponent` (sketches, extrudes, bodies) instead of creating a child component, unless the document is already a multi-component assembly.
- **A sketch on a non-XY construction plane (e.g. `yZConstructionPlane`) does not necessarily map its local (u,v) axes to (Y,Z) in the obvious order or sign.** In this project, `yZConstructionPlane` local `(u, v)` mapped to world `(X=0, Y=v, Z=-u)` — i.e. local-U was world-Z **negated**. A sketch built assuming a naive (u→Y, v→Z) mapping places geometry at the mirrored/wrong location while reporting success and correct-looking 2D coordinates in the sketch's own frame. Before trusting any cross-plane sketch position, check `sketchPoint.worldGeometry` (world coordinates) against `sketchPoint.geometry` (plane-local coordinates) for at least one known point and derive the actual mapping empirically; don't assume it from the plane's name.
- **`ExtrudeFeatureInput.setDistanceExtent(flag, distance)`'s first argument is a direction-flip boolean, not an "is-symmetric" flag** — despite reading naturally as one. Passing the "wrong" boolean silently extrudes/cuts away from the target body into empty space (see the point-containment note above for how to catch this). There's no reliable a-priori way to know which boolean value is correct for a given sketch/plane combination — create the feature, immediately run a `pointContainment` check at the intended cut location, and flip the boolean if it didn't take effect.
- **`TimelineObject` has no `deleteMe()`.** Call `timelineObject.entity.deleteMe()` (the underlying feature/sketch object) instead. Delete from the end of the timeline backward if removing multiple items, since indices shift after each deletion.
- **The screenshot tool's named camera directions (`top`, `bottom`, `left`, `right`, `front`, `back`) do not necessarily correspond to the faces you'd intuitively expect from the model's own working axes** (e.g. the "PCB-plane" face vs. the "connector wall" face). Don't assume a direction name maps to a specific feature; take one, check the visible aspect ratio against the known bounding-box dimensions to identify which pair of faces you're looking at, and iterate directions from there. The iso views (`iso-top-left`, `iso-bottom-right`, etc.) are more reliable for a first "does this look right" check since they show three faces from a consistent oblique angle.
- **Prefer a full through-hole for enclosure mounting bosses (boss + floor) over a blind hole from the top**, unless the user asks for the opposite — it's the more common real-world assembly pattern (screw inserted from below/outside, threading up into the boss) and was what a "properly open the screw holes" follow-up request turned out to mean in practice. If you do build a blind hole, say explicitly which side is open and which is closed so the user can catch a mismatch with their intended assembly method early.

### Two-part clamshell with the PCB clamped by common screws (Game Five pattern)

- **Common-screw stack**: TOP deck gets Ø2.8 clearance holes at the PCB mounting-hole coordinates → PCB MH Ø2.8 → BOTTOM boss pilot Ø2.1 (M2.5 self-tap, ~8 mm deep). One M2.5×~18 per corner clamps lid + board + tray; no separate lid fasteners. Boss top sits at PCB-underside Z so the board rests on the bosses.
- **Size button holes from the switch's PLUNGER diameter (datasheet), not the body**: EVQQ1 (Ø6.2 plunger, round) → Ø10 finger hole; Omron B3F-1025 (Ø3.5 plunger) → Ø5. Check the minimum web between adjacent holes stays printable (≥ ~4 mm for a D-pad cluster).
- **R1 perimeter rounding, robust edge pick**: collect edges whose BOTH vertices lie at the target face's Z (tolerance 1e-5 cm) AND whose bounding box touches the outer boundary within 1 mm; fillet that collection. Works on lid top face and tray bottom face without touching hole rims.
- **After ANY hole-size/geometry change, re-audit the verification probes**: enlarging a hole can swallow a previously-solid `pointContainment` probe point (a Ø8→Ø10 change put a "web is solid" probe inside the hole; the gated export then refuses for a false reason). Probes are part of the model — maintain them with it.
- **`document.activate()` does NOT persist across separate MCP execute calls** — the next call sees whatever document the app drifted to (often an untitled scratch doc). Find-doc + `activate()` + `adsk.doEvents()` + the actual work must be ONE script, with an assert on `app.activeDocument.name` before mutating.
- **Viewport captures for README/preview renders**: `viewport.saveAsImageFile(path, w, h)` works from scripts. Per-body shots toggle `body.isLightBulbOn` — but a single `adsk.doEvents()` is NOT enough; the hidden body renders as a translucent ghost in the PNG. Sandwich every state change with `viewport.refresh()` + a settle loop (`for _ in range(15): adsk.doEvents()`), then ALWAYS Read the PNGs back to verify before publishing. Faint background grid: `Commands.Start ViewLayoutGridCommand` executed without error but didn't remove it — acceptable for previews, don't burn time.

### Gentle slopes / raised display mound with temp-BRep only (no chamfer feature)

A "gently raised" plateau (e.g. +3 mm over the display with 7–8 mm slope bands on all sides) can be built deterministically from box booleans alone: UNION a rectangular mound block onto the deck, then DIFFERENCE four **tilted cutting boxes**, one per side, each resting on the desired slope plane (`OrientedBoundingBox3D.create` accepts arbitrary axes: axisA = slope direction `(run, 0, rise)` normalized, axisB = the edge direction, center offset half-a-thickness along the plane normal). Two bugs that both shipped a broken body before being caught by probes:
- **Start each cutting box AT the mound base edge, extending up-slope only** (center = base_point + dir̂·len/2). A cut box centered on the slope MID extends down-slope past the base, and the extended plane keeps descending — it shaved the surrounding deck 10+ mm away (probe "deck right of mound" caught it).
- **Never swap the two axes to fix a downward normal** — the box lengths are bound to the axes, so swapping reassigns lenA/lenB and the cut explodes in the wrong direction. The box is symmetric: keep the axes, and just NEGATE the normal for the center-offset when `(A×B).z < 0`.
Corners between adjacent slope cuts miter themselves automatically. Verify with probes ON the slope (low point solid, high point empty) AND on the deck beyond every side of the mound.

### More clamshell/case lessons (Game Five bottom tray)

- **Through-cut membranes**: a wall opening (USB slot) that cuts the outer wall but starts 0.5 mm short of an inner feature (the PCB ledge) leaves an invisible skin — looks open from outside, blocked inside. Cut wall openings from well INSIDE the cavity through past the outer face, and probe BOTH zones (`ledge zone empty` + `wall zone empty`), not just one.
- **Tie feature heights to the PCB datum, not absolute Z**: USB slot bottom = `Z_PCB − 6.0`, boss tops = `Z_PCB` — then a cavity-height change (user revised 15 mm → 10 mm mid-project) tracks automatically and only the probes' Z values need review.
- **Speaker grille**: concentric rings of Ø2 holes (center + r4/6 + r8/12 + r12/18 ≈ Ø28 pattern) cut with cylinders spanning from below the floor to `FLOOR+0.5`; parametrize the grille center so it can follow the speaker's final position. A sealed cavity muffles the speaker — offer the grille proactively whenever a speaker lives in a closed case.
- **Keep the probe suite in the SAME script as the geometry and gate the export on it** (`EXPORT SKIPPED - verification failed`). Both slope-cut bugs above were caught pre-export by exactly this gate.

### Fusion MCP bridge health (curl/JSON-RPC driving)

- **Add-in hang signature**: TCP connect to 127.0.0.1:27182 succeeds but every POST gets "Connection reset by peer" — Fusion itself is alive, only the MCP add-in is dead. Do NOT kill Fusion autonomously (unsaved docs risk). Cure that worked: the user re-ticks the **"Fusion MCP サーバ" checkbox in Fusion's preferences** (or toggles the add-in via Shift+S) — no Fusion restart needed, session works immediately after.
- Driving without an MCP client: `initialize` (protocolVersion 2024-11-05) → grab `Mcp-Session-Id` header → `notifications/initialized` → `tools/call fusion_mcp_execute {featureType:"script", object:{script}}`. Responses may be SSE (`data: {...}` lines) OR plain JSON — parse both. Screenshots: `tools/call fusion_mcp_read {queryType:"screenshot", direction:"iso-top-right", width, height}` → base64 image content. Keep `fusion_exec.py <script.py>` / `fusion_shot.py <dir> <png>` helpers in the scratchpad.
